# Orbit-informed BBR cwnd target

This track actually implements and evaluates a narrow geometry-informed target,
separate from forecast loss-threshold protection. Read the
[predeclared experiment](../../docs/experiments/20261012-orbit-bdp.md).

All four declared simulations completed. The 100Mbps pair has identical delivery,
queue and drop traces despite changed internal targets/cwnd. The 10Mbps pair has
unchanged event-window delivery, 1,380 fewer app bytes by 40s, higher mean served
queue wait, but lower maximum steady-window wait and one fewer TcDrop event.
This tested policy did not demonstrate a throughput improvement. Results and
source/runtime/input/raw hashes are linked in the experiment record.

During normal ProbeBW only, substitute the operator's predicted two-direction
propagation RTT in the BDP term of the cwnd target. Look ahead by the current
geometry RTT. Preserve BBR's measured maximum bandwidth, cwnd gain, quantum and
ACK aggregation allowance. STARTUP/DRAIN/ProbeRTT, measured RTprop and its expiry,
pacing/gain-cycle decisions and recovery remain unchanged. OFF is the default.
This does not estimate queue delay, update the measured RTprop, or receive exact
bandwidth/queue truth. Geometry omits serialization and notification error.

Use **one complete `ns3.patch`** on a fresh official ns-3 volume. Do not also apply
the observer patch: it is already included. `ns3-initial-build-failure.patch` is a
preserved unsuccessful development artifact and must not be used.

```powershell
$orbitRoot = (Resolve-Path .).Path
$orbitImage = 'ghcr.io/yeonjong21/cs30401-lab1@sha256:3cb4877c73b4ae5e3542c1567b6761a8913056dd429d8a18f7c40aeeb399b3b4'
docker run -d --name orbit-bdp-replay --cpus 2 --memory 4g --mount "type=bind,source=$orbitRoot,target=/work" --mount 'type=volume,source=orbit-bdp-replay-ns3,target=/home/ubuntu/ns-3.48' $orbitImage sleep infinity
docker exec -w /home/ubuntu/ns-3.48 orbit-bdp-replay bash -lc 'git apply --check /work/code/orbit-bdp/ns3.patch && git apply /work/code/orbit-bdp/ns3.patch && git add -N scratch/main_satnet/bbr_route_observer.h && ./ns3 build -j 1'
docker exec orbit-bdp-replay python3 /work/code/orbit-bdp/run.py bbr100-base40 bbr100-orbit40 bbr10-base40 bbr10-orbit40 --root /tmp/orbit-bdp-replay
docker exec orbit-bdp-replay python3 /work/code/orbit-bdp/analyze.py --root /tmp/orbit-bdp-replay --out /tmp/orbit-bdp-replay-summary
```

The provided `geometry.csv` was regenerated from the supplied state using its
official `path_truth.py`; all 2,000 rows exactly match the prior recorded geometry.
`geometry-receipt.json` gives identities. It can be regenerated by writing the
official truth CSV to `/tmp/orbit-bdp-path-truth.csv`, then using `run.py --prepare`
in a checkout where `geometry.csv` does not already exist. Existing files/runs
are never overwritten. Analysis uses Python's standard library and reuses the
versioned passive-observer validation helper.

Each simulation has a 240-second wall cap, one at a time within this track. The
four 40-second cases compare paired 100/10Mbps links with 100-packet queues,
one paced bulk BBR flow, and the identical supplied route state. This is not a
200-second result, modern BBRv3 experiment, perfect-order guarantee, or real
operator notification implementation. The analysis verifies actual ordered
application delivery, source-bin accounting, queue conservation, execution output
hashes, paired inputs and actual target changes; drop layers stay separate.
