2026-10-14, Seongchan Kim. 실행 소스 checkpoint: `44f0850c2eb0fe3127993601822a55f502dfbd05`. ns-3 patch SHA-256: `8f822979eb9556c1f27f5128a462d66f085b1554ab3366c9af2c4036df8d7997`.

**공격적 ELT는 기존 tail 보완이 놓치던 21-MSS 짧은 전송을 개선했다. 그러나 이번 적용에서는 75초 큐 적체·드롭을 해결하지 못했다. 기본 제출 코드로 교체할 근거는 아직 부족하다.** 기존 PR #16, 보고서와 제출 ZIP은 변경하지 않았다.

## 먼저 구분할 문제

기존 1-MSS tail은 대기 중 마지막 미송신 세그먼트 한 개 때문에 파일 완료가 한 RTT 늦어지는 문제를 보완했다. 자연 LEO 대용량 전송에서는 tail admission이 0회였으므로, 이것을 75초 큐 문제의 해결책으로 이해하면 안 된다.

[RFC 4653](https://www.rfc-editor.org/rfc/rfc4653.html)은 재정렬에 따른 손실 판정을 지연하면서 전송을 이어가는 Extended Limited Transmit과 종료 시 창 조정 규칙을 제안한다. Aggressive는 전송을 더 유지하고 Careful은 일부 허용량을 남겨 둔다. RFC 자체도 실제 손실의 지연, 수신 버퍼 요구량, 혼잡 대응 지연의 비용을 설명한다. 따라서 큐 폭발을 자동으로 없애는 알고리즘으로 전제하지 않았다.

## 이번에 실제로 구현한 범위

기존 궤도 기반 선택적 대기 안에서만 두 ELT 송신 방식을 구현했다. 시작 전 누적 미확인 데이터 `F0`를 고정하고, 새 데이터가 `pipe + Skipped + MSS <= F0`일 때만 기존 송신 경로를 통해 전송한다. Careful은 송신마다 추가 Skipped를 적립한다. 기존 tail과 중복 적용하지 않는다. 수신 창, 실제 송신·재전송 계수, PRR와 RTO, 원래의 6.631518-ms 대기 기한은 유지했다.

**완전한 RFC 4653 TCP-NCR 구현은 아니다.** 첫 SACK부터 시작하는 RFC와 달리 첫 선택적 손실 유예부터 시작하고, K=3과 짧은 대기를 유지한다. RFC의 적응적 DupThresh, 약 한 RTT 대기, T4 재시작, F0/2 복구 backoff는 적용하지 않았다. 따라서 이 결과를 전체 RFC 알고리즘의 성공·실패로 일반화할 수 없다. 자세한 차이는 [SOURCE_NOTE.md](SOURCE_NOTE.md)에 있다.

또한 `F0`는 현재 cwnd나 실제 네트워크 내 패킷 수와 같지 않다. 미세 실험에서 앞선 두 ACK가 보낸 정상 대체 데이터를 포함하여 `F0=12 MSS`, `cwnd=10 MSS`, SACK 처리 후 `pipe=9 MSS`였다. 그래서 새 SACK 1 MSS를 받은 첫 ACK에서 Aggressive는 3 MSS, Careful은 2 MSS를 보냈다. **새 SACK 하나에 패킷 하나를 보내는 단순한 추가 크레딧 방식이 아니라, 고정된 진입 flight 안의 여유를 사용하는 적용이다.** 이 차이를 숨기지 않았다.

## 짧은 파일: 도움이 되는 경계와 안 되는 경계

100 Mbps, 편도 지연 50/50 ms, 큐 2,000패킷, MSS 1,380 B, 첫 원본 데이터 패킷 한 개 실제 손실. 경로는 바뀌지 않으며, selective 계열에는 이전 연구와 같은 잘못된 단축 예측을 넣었다. 실제 손실·오예측 비용을 보는 대조 실험이며 자연 LEO 성능 결과가 아니다. 아래는 전체 파일의 순서 있는 APP 전달이 완료된 FCT이다.

| 파일 크기 | 원본 CUBIC | 선택적 대기 | 기존 1-MSS tail | ELT Aggressive | ELT Careful |
|---|---:|---:|---:|---:|---:|
| 20 MSS / 27,600 B | 251.510 ms | 350.482 ms | 257.224 ms | 257.224 ms | 350.827 ms |
| 21 MSS / 28,980 B | 350.482 ms | 350.597 ms | 350.597 ms | **257.224 ms** | 350.941 ms |
| 24 MSS / 33,120 B | 351.285 ms | 350.941 ms | 350.941 ms | 350.827 ms | 357.343 ms |

21 MSS에서 기존 tail은 미송신 데이터가 한 MSS보다 많아 7회 거절하고 한 번도 admission하지 않았다. Aggressive는 대기 중 총 9개의 원본 세그먼트를 보냈다. 마지막 원본 세그먼트 송신이 `300.482400→201.165760 ms`로 앞당겨져 FCT가 **93.373442 ms, 약 26.63%** 줄었다. 원본 CUBIC보다도 93.258722 ms 빨랐다.

다만 20 MSS는 기존 tail과 같고 원본보다 여전히 5.713758 ms 느리다. 24 MSS의 tail 대비 이득은 0.114720 ms뿐이다. Careful은 세 크기 모두 tail보다 느리다. 단일 유리한 크기로 보편적 FCT 개선을 주장하지 않는다.

모든 미세 실험의 실제 손실·재전송·복구 진입은 각각 1회다. 동일한 첫 원본 데이터는 150.128320 ms에 드롭됐다. 원본은 200.477440 ms, 대기 계열은 모두 207.108958 ms에 재전송했다. **실제 손실 복구 지연 6.631518 ms가 없어지지 않았다.** 21-MSS 이득은 마지막 새 데이터의 한 RTT 정체를 피한 결과다. 미세 실험의 모든 ELT 종료는 deadline이었고 CACK 종료 창 조정은 실행되지 않았다.

## 자연 LEO 200초: 큐 해결 효과 없음

PR #16과 동일한 Seoul–London 캐시 토폴로지, 10 Mbps, 100패킷 큐, CUBIC/SACK/PRR, 100-GB 단일 흐름, 200초, pacing off. 위성 전체 경로를 새로 탐색하지 않고 기존 캐시와 예측 테이블을 사용했다.

| 정책 | 전체 APP goodput | 전체 데이터 드롭 | 전체 재전송 / 복구 | 75초 직후 평균 송신 큐 | 같은 구간의 완료된 큐 방문 평균 대기 |
|---|---:|---:|---:|---:|---:|
| 원본 CUBIC | 9.544356 Mbps | 499 | 523 / 41 | 53.271 패킷 | 59.623 ms |
| 기존 선택적 대기 + tail | 9.5465088 Mbps | 486 | 507 / 40 | 87.232 패킷 | 96.200 ms |
| ELT Aggressive | 9.5465088 Mbps | 486 | 507 / 40 | 88.525 패킷 | 97.613 ms |
| ELT Careful | 9.5465088 Mbps | 486 | 507 / 40 | 88.525 패킷 | 97.613 ms |

직후 큐·대기 구간은 `[75.0,75.5)`초다. 큐는 정확한 시간 적분 평균이고, 대기는 해당 구간에 서비스 완료된 **송신 지상국 장치 방문**의 평균이며 RTT가 아니다. 드롭은 flow/tx-id/tx-time/seq/payload의 완전한 송신 식별자로 결합한 실제 데이터 손실이다.

`[74.5,77.5)`초에서는 tail/Aggressive/Careful 모두 **드롭 11개, 재전송 12회, 복구 2회**다. 이 구간 전체 평균 큐는 48.718→48.249패킷으로 조금 낮지만, `[75,75.5)`초 큐는 87.232→88.525로 높다. 전체 200초 평균 송신 큐도 36.098→36.139로 조금 높다. 선택한 한 구간의 감소만을 큐 개선으로 보고하지 않는다.

실제 selective wait는 세 정책 모두 26.2초 이벤트에서 한 번만 시작했다. Aggressive/Careful은 그때 각각 3/2개의 원본을 보냈으며 **75초 구간의 wait·ELT 송신은 모두 0회**다. 26.2초 주변 `[25.7,28.2)`초의 불필요한 재전송·복구는 기존 tail과 두 ELT 모두 0/0이고 원본은 3/1이다. 기존 메인 알고리즘의 이득을 ELT의 새 이득으로 계산하지 않는다.

대용량 ELT의 정상 ACK 종료는 26.329936038초에 한 번 관측됐다. 두 방식 모두 종료 공식으로 cwnd가 **162,840→165,600 B**, ssthresh가 **139,380→165,600 B**가 됐다. 이 입력에서는 종료 공식이 창을 줄인 것이 아니므로 “anti-burst가 큐를 억제했다”는 실증 근거도 없다. 75초 변화는 이전 송신/창 변화에 따른 경로상의 간접 영향이며 직접 ELT 개입이 아니다.

## 검증 및 판단

- 사전 고정한 15개 미세 실험 + 4개 자연 LEO 실험을 모두 실행했다. 19개 모두 종료 성공 및 소스/실행 바이너리/입력 불변 검사 통과; 미세 실험은 전량 APP 전달 완료.
- 원본/기존 selective/tail 대조군 7개에 대해 이전 측정 CSV **75개가 바이트 단위로 일치**했다. [off-parity.json](results/off-parity.json)은 과거 수치로 새 결과를 생성하는 입력이 아니라 체크섬 대조 기록이다.
- 새 로그에서 송신 전후 E2 조건, 고정 F0, Careful Skipped, 수신 창, 한 번의 원본 TX, 고정 deadline, 관측된 CACK 종료 공식을 검사했다. [summary.csv](results/summary.csv)와 [metrics.json](results/metrics.json)에 전체 조건과 불리한 결과도 포함한다.
- 첫 빌드는 C++ 자료형 오류로 실패했고, 정책을 바꾸지 않은 타입 수정 후 성공했다. Windows worktree Git 경로의 컨테이너 접근 실패로 발생한 최초 launch도 시뮬레이션 실행 전이었다. 두 실패 흔적을 보존했으며, 성공한 19개 결과와 섞지 않았다. 컨테이너에서는 host Git commit을 검증했다고 주장하지 않고 host-declared checkpoint와 실제 파일/patch/runtime 해시를 함께 기록했다.

**권장 결정:** Aggressive를 짧은 파일 경계 문제의 후속 후보로 남기되 제출 기본 정책은 유지한다. Careful은 이번 입력에서 채택하지 않는다. 큐 문제에는 pacing/송신 버스트/큐 정책처럼 실제 큐에 작용하는 별도 제어가 필요하며, ELT를 그 근본 해결책으로 주장하지 않는다. 다중 경쟁 흐름, 부분 세그먼트, pacing on, 오예측 강도 및 더 넓은 크기 범위는 아직 미검증이다.
