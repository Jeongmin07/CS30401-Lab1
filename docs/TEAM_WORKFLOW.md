# 조원 3명 + 각자의 AI가 함께 작업하는 방법

## 무엇을 공유하는가

다른 노트북에서 진행 중인 일을 AI가 확인하려면, 그 정보가 GitHub에 올라와 있어야 한다. 공유된 기록을 읽는 방식이며 자동 실시간 통신이나 중앙 AI 관리 시스템을 가정하지 않는다.

| 공유할 정보 | 위치 |
| --- | --- |
| 담당 조원, 목표, 질문, 막힌 점 | 작업별 GitHub Issue |
| 진행 중인 코드와 변경 범위 | 작업 브랜치와 Draft PR |
| 마지막 진전과 인수인계 | 그 브랜치의 `docs/work/<github-login>.md` |
| 실험 조건, 명령, 실제 결과, 해석 | `docs/experiments/issue-<번호>-<run-id>.md` |
| 합의된 연구 방향과 공통 조건 | `docs/PLAN.md` |

**Draft PR과 작업 기록은 `main`에 없어도 확인할 수 있다.** 새 AI는 GitHub의 열린 PR을 찾고, 그 PR의 브랜치 파일을 읽어야 한다. 다른 사람의 로컬 변경과 아직 push하지 않은 결과는 확인할 수 없다.

## 작업 하나의 흐름

1. **작업 범위를 정한다.** Issue에 담당 조원 한 명, 목표, 수정 범위, 완료 기준, 의존하는 작업을 적는다. 조원 이름으로 담당하고 AI 모델 이름을 담당자로 쓰지 않는다.
2. **겹치는 작업을 확인한다.** 최신 Issue와 Draft PR을 읽고 같은 파일/실험이 진행 중인지 확인한다. 조원끼리 범위를 합의한다.
3. **작업 브랜치를 만든다.** 작업 하나는 검토 가능한 결과물 묶음이다. 분석 도구 하나를 완성하는 동안 여러 대화와 실험을 해도 같은 브랜치를 사용한다.
4. **진행 중인 내용을 보이게 한다.** 시작 기록이나 초기 코드를 push하고 Draft PR을 연다. 담당 Issue와 작업 기록을 연결한다.
5. **중요한 시점에 갱신한다.** 실행 가능한 코드, 의미 있는 실험 결과, 실패, 조건 변경, 의존성 변경이 생기면 기록과 브랜치를 공유한다. 작업을 마치거나 다른 조원에게 넘기기 전에도 갱신한다.
6. **검토 후 합친다.** 완성된 PR에는 실행/검증 결과와 한계를 적고 Draft를 해제한다. 다른 조원 한 명이 확인하고 합의된 병합 담당자가 `main`에 합친다. 이 규칙은 팀의 작업 약속이며 저장소 보호 설정을 추가한 것은 아니다.
7. **다음 작업은 새로 시작한다.** 병합된 브랜치를 계속 누적 사용하지 않고 최신 `main`에서 다음 작업 브랜치를 만든다.

코드를 바꾸지 않고 기존 명령으로 실험만 했다면 Issue에 결과를 기록해도 된다. 새 분석 코드나 재현 가능한 실험 문서가 생기면 PR로 제출한다. 공유 권한은 각 조원의 작업 지시를 따른다.

## 다른 노트북의 작업을 확인하는 예

아래는 저장소를 clone한 폴더에서 실행하는 읽기 명령이다. GitHub CLI 또는 연결된 GitHub 도구를 사용할 수 있다.

```bash
git status --short
git fetch origin
gh issue list --repo Jeongmin07/CS30401-Lab1 --state open
gh pr list --repo Jeongmin07/CS30401-Lab1 --state open
```

관련 PR을 찾으면 PR 설명/댓글, diff, 브랜치의 작업 기록을 읽는다. 아래 번호와 브랜치/아이디는 실제 값으로 바꾼다.

```bash
gh pr view 12 --repo Jeongmin07/CS30401-Lab1 --comments
gh pr diff 12 --repo Jeongmin07/CS30401-Lab1
git show origin/feat/plot-tcp-traces:docs/work/member-login.md
```

다른 브랜치의 문서를 읽기 위해 현재 작업 브랜치를 바꾸거나 로컬 변경을 지울 필요는 없다. 다른 PR에 의존하는 코드는 그 PR 번호와 사용한 commit을 적고, 우선 `main` 병합을 기다리는 방식을 기본으로 한다. 급히 먼저 사용해야 하면 조원끼리 명시적으로 합의한다.

## 브랜치와 파일의 소유 범위

- 브랜치는 사람별 영구 공간이 아니다. 예: `setup/lab-env`, `feat/plot-tcp-traces`, `experiment/cubic-bbr-60s`.
- 한 사람이 한 작업 브랜치를 맡고, 자기 AI가 그 브랜치에서 계속 작업한다. 다른 조원의 브랜치에 임의로 commit/push하지 않는다.
- `docs/work/<github-login>.md`는 해당 조원이 자기 브랜치에서 관리한다. 다른 조원의 기록을 고쳐 진행 상황을 대신 확정하지 않는다.
- 서로 다른 실험 기록은 Issue 번호와 run ID로 구분한다. 여러 사람이 `E001.md` 같은 동일 파일을 동시에 만들지 않는다.
- 공통 분석 도구와 공통 조건이 필요한 작업은 먼저 작은 PR로 합친다. 각자 서로 다른 방식으로 계산한 수치를 그대로 비교하지 않는다.

## 실험 결과 공유

원본 state와 대용량 로그는 각 노트북에 둔다. Git에는 재현 코드/설정, 작은 요약표, 핵심 그래프와 실행 기록을 올린다. 다른 조원이 원본 검증을 위해 로그가 필요하면 접근 가능한 공유 위치를 합의하고 기록에 남긴다. 로컬 파일 경로만으로는 다른 노트북이 접근할 수 없다.

실험 기록에는 다음을 반드시 구분한다.

- **관측:** 실제 실행에서 얻은 수치와 변화.
- **가설:** 그 현상의 원인이라고 추정하는 설명.
- **검증:** 원인을 확인하기 위해 한 대조 실험과 그 결과.
- **미확인:** 아직 실행하지 못한 것, 재현되지 않은 것, 원본 접근 제한.

코드 commit, Docker 이미지 tag, 적용한 patch/해시, seed, TCP 종류, 링크 속도, 큐, flow, 시간, 실행 명령을 기록한다. 실험 실행 이후 코드가 바뀌었다면 실행 당시 commit을 유지해 적는다. 짧은 문법 검사 성공과 실제 시뮬레이션 성공도 구분한다.

## Docker와 ns-3 변경

각 노트북의 Docker volume은 별개다. GitHub에서 pull해도 volume 안의 C++ 변경은 전달되지 않는다. 공식 환경 안에서 patch를 만든 뒤 자신의 PR에 포함한다.

```bash
make_patch.sh /work/code/ns3.patch
```

여러 조원이 동시에 C++를 수정할 때는 자기 실험에서 적용한 patch를 별도 파일로 보존하고 기록한다. 여러 patch를 동일한 `code/ns3.patch`에 각각 덮어쓰거나 임의로 이어 붙이지 않는다. 겹치는 변경을 통합한 최종 patch는 지정된 담당자가 만들고 깨끗한 환경에서 재현을 확인한다.

## 최소 운영 약속

조원끼리 연구 방향과 담당 작업을 정한다. 각 AI에게는 시작할 때 `docs/START_HERE.md`의 프롬프트를 전달한다. 새 작업 시작, 중요한 단계 전환, 인수인계 때 최신 GitHub 기록을 읽게 한다. 모든 응답이나 도구 호출을 기록할 필요는 없다.

다른 조원의 결과를 읽은 AI는 무엇을 재사용할지, 어느 commit/실험을 근거로 삼았는지, 무엇을 아직 확인하지 못했는지 설명한다. 서로의 가설을 반복하는 대신 실제 코드와 실험 근거를 확인한다.
