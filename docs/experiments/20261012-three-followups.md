# 세 가지 예측 제어 후보의 제한된 후속 검증

2026-10-12, kim-seongchan. 사용자가 [고찰](../research/20261012-progress-retrospective.md)의 세 후보를 진행하도록 승인했다. CUBIC 확대와 축소는 문제의 전제를 빠르게 확인하고 근거가 없으면 중단한다. 선택적 손실 대기는 구현과 실제 손실 비용까지 검증한다. 팀 최종 주제와 다른 조원의 역할을 확정하는 기록은 아니다.

**후속 검증을 완료했다.** 확대와 축소는 선언한 문제의 근거가 부족해 정책 구현 전에 중단했다. 선택적 손실 대기는 최종7조건을 실제로 비교했다. 자연 LEO에서 기존 bounded K20과 같은 작은 전체 이득을 냈다. 동일 패킷을 주입한 한 LEO 손실 대조에서 첫 재전송의 추가 지연은5.735961ms였다. 잘못된 예측 힌트를 준 짧은 흐름에서는 완료 시간이 약39.35% 늘었다. 아래에 최초 선언을 보존하고 완료 결과와 적용 한계를 연결한다.

여기서 LEO 경로는 제공 서울–런던 ns-3/Hypatia 시뮬레이션 경로다. 실제 손실은 그 모델 안에서 패킷이 실제로 삭제된 사건을 뜻한다.

첫100Mbps passive CUBIC 원본은 확대 담당의 별도 공식 volume에서 한 번 실행하고 축소 담당과 공유한다. 정책·source·runtime은 실행 도중 바꾸지 않는다. 후보별 별도 source volume, CPU2·메모리4GiB·build1job, 실행별240초 wall cap을 출발 예산으로 사용한다. 최초 simulation 전에 이 선언과 각 소유 범위의 계획을 GitHub에 공유한다.

확대·축소의 gate가 통과할 경우만 각각 같은 조건의 정책ON 최대1회와 필요 실제손실micro1회를 추가한다. 조건을 성공할 때까지 탐색하거나 RTT를 인위적으로두배 늘리지는 않는다. observer-off와 baseline 동등성, 실제 정책 작동, 설정/source/runtime/input/output 해시와 실제 수신량을 보존한다.

손실 대기의 출발 규칙은 전환 epoch 동안 이미 송신한 미확인 패킷 중 재전송·기존 loss가 아닌 같은 old-flight cohort 후보들을 보호하는 것이다. loss marking과 socket의 복구 진입을 일관되게 다루고, 첫 손실 의심 증거에서 기하 기반의 짧은 timer를 시작한다. 여러 후보 hole은 하나의 episode deadline을 공유하며 head가 이동해도 기한을 연장하지 않는다. 정방향 지연 감소가 1ms 이상인 전환만 선택하며 대기시간은 `clamp(2×정방향 전파 지연 감소, 1ms, 20ms)`를 사전 후보값으로 사용한다. 패킷 허용량은 명목 흐름률과 정방향 감소의 곱에서 구한 예산이며 정확한 최대 추월 상한이라고 부르지 않는다. epoch의 폭과 episode 대기시간은 구분한다. 기본 RTO와 SACK/PRR 정보는 유지하며 cohort 밖의 기본 손실 표시·기존 복구가 시작되면 보호를 중단한다. 실제 물리 drop을 알리는 평가 정보는 guard 입력이 아니다.

처음 선언의 head-only 최소 구현은 첫 실행 전 소스 검토에서 수정했다. 기존 26.2초 SACK는 세 old-flight hole을 동시에 표시하며, TxBuffer가 뒤쪽 hole들을 먼저 loss로 표시하므로 head만 보호하면 확인된 문제에 개입할 수 없다. 새 성능 결과를 보고 범위를 확대한 것이 아니라 이미 공유된 packet 증거로 이 구조적 문제를 확인한 수정이다.

손실 후보의 최초 출발 집합은 같은 LEO10 원본·기존 bounded K20·새 정책3회, stable20MSS 실제 첫 손실 원본·새 정책의 잘못된 positive hint2회, 실제 경로 단축 시점에 명시적으로 주입한 old-flight 실제 손실 원본·새 정책2회까지 최대7회다. 실제 손실 선택 규칙은 시각·전송 조건으로 미리 정하고 미래 실행에서 유리한 sequence를 고르지 않는다. 구현 검토에서 안전한 소스 경로나 입력 가정이 바뀌면 첫 실행 전 수정 사유를 기록한다.

예비 micro2회 이후 읽기 교차 검토에서, head가 전진해 CA_OPEN으로 돌아온 경우 deadline의 SACK 재평가만으로 복구 송신을 깨우지 못할 수 있는 소스 경계를 확인했다. 최종 구현은 실제 head loss 표시가 있는 OPEN에만 DISORDER 상태 통지를 거쳐 기존 복구를 호출하며 등록 종료에도 같은 재평가 경로를 사용한다. fake ACK·dupACK 수 변경·수동 cwnd 변경은 없다. 예비2회 원본·source·runtime은 보존하고, 수정한 최종 source 하나로 micro2회와 LEO5회를 비교한다. **최종7조건과 개발 예비2시도를 구분한다.** 파라미터를 결과에 맞춰 조절한 것이 아니라 복구 경계 수정에 따른 재검증이며, 예비 first-head 대조로 OPEN 경로의 실행 검증을 주장하지 않는다.

전체 및 고정 전환창의 앱 수신 goodput, 재정렬·재전송·복구, 장치 큐·drop, 실제 손실 복구 시각과 유한 흐름 완료 시간을 후보에 맞춰 평가한다. drop hook과 고유 손실, SRTT와 직접 queue wait를 구별한다. 읽기 진단·미구현 중단·실제 작동·실행 실패를 구분하고 실패·timeout 부분 결과는 성능 분석에서 제외한다.

위 내용은 실행 전 선언과 개발 중 수정 사유이며, 아래는 완료 후 결과다.

## 확대와 축소의 선별 종료

현재 완료한 10Mbps 관측 원본은 기존 측정8CSV와 동일했다. 최대 경로 연장 187.4초에서 cwnd-limited 자체는 있었지만 송신자 GSL의 직렬화 점유는 앞뒤0.5초와 고정2.5초창 모두100%였다. 단순 윈도우 부족 때문에 송신 링크가 놀았다는 가설은 이 조건에서 입증되지 않았다. [확대 선별 결과](20261012-orbit-cubic-up.md)

단축 구간의 큐는 변화했다. 75초의 송신 장치 평균 served queue wait는 약48.90→59.62ms로 증가했지만, 조사한 완료 조건의 단축 평가창에서 실제 drop은0이었다. 재정렬/복구와 큐 적체를 구분해, 선언한 overflow 방지 후보는 정책 구현 없이 중단했다. [축소 선별 결과](20261012-orbit-cubic-down.md)

공유100Mbps/q100/200초 관측은240.101초 wall cap에서 timeout으로 종료되어 성능 분석에서 제외했다. 그 조건의 정책 효과가 없었다고 결론내리지 않으며 해당 조건은 미검증으로 남긴다. 재실행·추가ON·토폴로지 생성으로 선별 예산을 확대하지 않는다.

## 선택적 손실 대기의 실제 결과

[세 번째 후보의 실험·원본 연결](20261012-orbit-loss.md)과 [한 번에 적용하는 patch 및 재현](../../code/orbit-loss/README.md)을 읽는다. 최종 구현은 K3를 유지하면서 전환 때 이미 보낸 미확인 원본 cohort에만 짧은 대기를 준다. 여러 hole은 첫 손실 의심 시각에 정한 기한을 공유하며 이후 ACK/SACK로 기한을 연장하지 않는다. 수신 확인·예산 초과·기한·기존 복구에서 기본 TCP로 돌아간다.

실제 LEO 손실 대조의 전체 goodput은9.5441904→9.5442456Mbps로1MSS 차이다. 첫 창은9.472320→9.476736Mbps, 재전송2→1이며 복구는 둘 다1회다. 100GB 흐름은200초 안에 끝나지 않으므로 이 대조를 FCT 개선으로 부르지 않는다. 짧은 흐름의0.400114720초 bounded K20 값은 과거 자료이며, 최종 V2 micro에서 새로 실행한 세 번째 대조가 아니다.

두 실제 LEO 손실 실행은 동일한 원본을 잃었다: flow0, tx_id21820, seq29681041,1380B, 송신26.152017749초, 수신 장치의 실제 drop26.235726816초, node1585/device1. 평가용 태그·drop 정보는 정책 입력으로 쓰지 않는다. 물리 drop과 선택 기록의 전체 식별자·수신 시각을 연결하고, drop 이전 재전송을 이후 복구 지연 계산에서 분리했다. 이 분석 보강은 모든 실행이 끝난 뒤 했으며 정책·τ·예산·선택 규칙은 바꾸지 않았다.

기존 bounded K20과 새 selective의 등록기간은 같은 공식이지만 기하 표본·정밀도가 다르다. 26.2초에서195.396000/195.390816ms,75초에서181.974000/181.977820ms다. 새 입력은 같은 시각의 old/new 정방향 경로를 따로 계산했으며 성능 결과를 보고 시간을 조절하지 않았다. 이 미래 정보는 운영자의 정확한 routing·기하 힌트 가정이다. 공개 궤도만으로 실제 큐·패킷 도착·ACK 도착을 정확히 아는 구현은 아니다.

## 범위·검증·공유

이번 후속 작업은 **총11시도**다: 공유 passive 성공1·timeout1, V1 개발 micro 성공2, 최종 V2 성공7. 확대와 축소가 같은 원본을 공유한 것을 두 실행으로 세지 않는다. 최종 비교7과 예비2는 서로 다른 source/runtime이며 독립 반복 표본도 아니다. 앞선 네 후보21유효 실행과 손실 판정13조건은 별도의 역사적 자료다.

최종 손실 source checkpoint는 `730ea20936dd668c914c3ad3689231104134b592`다. 소스·실행기·runtime·입력·출력 해시와 실제 launch commit/dirty 상태는 각 manifest에 유지했다. passive 원본의 기존8CSV, 최종 micro 원본의 기존9CSV 동일성, shared deadline·K3 유지, 실제 수신량, 주입 손실의 물리적 식별자를 확인했다. 공식 최적화 build는 `NS3_ASSERT=OFF`이며, 보수한 OPEN 복구 분기는 최종7조건에서0회로 실행 검증되지 않았다. 소스 읽기 검토와 실행된 경계의 관측을 구분한다. 독립 전체 재실행·통계적 반복은 수행하지 않았다.

큰 CSV는 [새 원본 prerelease](https://github.com/Jeongmin07/CS30401-Lab1/releases/tag/orbit-followups-20261012)에 유효 passive·제외 timeout·예비 V1·최종 V2를 나눠 보관한다. 파일별 목록은 각 실험의 inventory, 업로드 byte/digest 확인은 [공통 Release receipt](assets/20261012-three-followups/release.json)에 있다. [문서·메타데이터 검증](assets/20261012-three-followups/verification.json)은 정적 문법·JSON·상대 링크·현재 파일 해시 검사이며 실행 재현을 대신하지 않는다.

이 작업에서 유지할 결론은 **예측으로 확인된 허위 복구를 줄일 수 있지만, 큰 전체 처리량 개선과 실제 손실 비용 해소는 달성하지 못했다**는 것이다. 선택적 대기는 기존 넓은 문턱 보호보다 대상을 제한하지만, 짧은 대기 자체가 작은 FCT 비용을 보장하지 않는다. 확대·축소의 새 정책ON,100Mbps timeout 재실행,τ/예산 sweep,새 토폴로지는 추가하지 않았다. 팀은 이 자료의 가정과 비용을 검토해 최종 보고서에 사용할 범위를 결정할 수 있다.
