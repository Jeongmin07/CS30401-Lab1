# 궤도 예측 RTT를 이용한 BBR cwnd 목표: 선언과 실제 결과

담당: kim-seongchan with AI assistance, 2026-10-12. PR16 작업 브랜치 안의 별도 실제 구현·실험이다. 손실 판정 유예 정책을 적용하지 않는다. 결과는 실행 뒤 추가하며 개선을 미리 가정하지 않는다.

## 질문과 정책

정확한 미래 경로 기하를 운영자가 송신자에게 알려 주는 조건에서, BBR의 cwnd 목표에 관측 최소 RTT 대신 예측 전파 RTT를 쓰면 수신량·큐 비용이 어떻게 바뀌는가? 전파 RTT는 제공 서울–런던 경로의 양방향 합이며 단방향 패킷 지연이나 실제 큐 RTT가 아니다. 직렬화 지연도 포함하지 않는다.

정책은 정상 ProbeBW에서 `현재 최대 대역폭 추정 × 미래 전파 RTT × 기존 cwnd gain`으로 BDP 항만 바꾼다. 미래 시점은 `지금 + 현재 기하 RTT`로 정한다. 이 한 RTT 선행은 ACK 피드백 시간 규모를 이용한 고정 후보이며 최적값이나 도착시간 상한으로 주장하지 않는다. 기존 gain·send quantum 여유·ACK aggregation 항은 유지한다. STARTUP/DRAIN/ProbeRTT·손실 복구·RTprop 측정/만료·pacing와 gain-cycle 판단은 바꾸지 않는다. 정책 기본값은 off다.

입력은 `code/kim-study/path_truth_200s.csv`의 기하 값뿐이며 큐 정답·패킷 도착 결과·링크 속도 정답을 BBR 제어에 넣지 않는다. 대역폭은 BBR가 실제 ACK로 추정한 값을 그대로 쓴다. 실제 RTT/SRTT와 원래 최소 RTT도 별도로 관측한다. 이 실험은 큐가 없어졌다고 RTT 차이만으로 선언하지 않고 실제 device queue 대기를 비교한다.

## 고정 실행 집합과 예산

제공 200초 state 중 첫40초, 100ms forwarding 갱신, 단일100GB 서울1584→런던1585 `TcpBbr` 흐름·pacing on·seed123456789. 모든 ISL/GSL의 큐는100패킷이다.

| case | 모든 링크 속도 | 정책 |
|---|---:|---|
| bbr100-base40 | 100Mbps | off |
| bbr100-orbit40 | 100Mbps | on |
| bbr10-base40 | 10Mbps | off |
| bbr10-orbit40 | 10Mbps | on |

두 링크 속도는 기존 고속 탐색과10Mbps CUBIC 관찰을 연결하는 제한된 대조이며 실제 Starlink 용량 보정값은 아니다. 경로·큐·흐름·TCP 입력은 각 쌍에서 동일하다. 주 평가창은 전체 `[0,40)`, 기동 이후 `[10,40)`, 확인된 경로 단축 주변 `[25.7,28.2)`다. 75초 창은 실행하지 않는다. 실패·timeout이면 불완전 자료를 성능 표에서 제외한다. 총4회, 개별 wall cap240초이며 필요하더라도 전체6회를 넘지 않는다. 새 토폴로지·APSP·무선 모델·파라미터 sweep은 만들지 않는다.

## 환경·검증·출력

전용 fresh 컨테이너 `lab1-orbit-bdp-20261012`, 새 volume `cs30401-orbit-bdp-ns3-20261012`, CPU2·memory cap4GiB, build `-j1`. 공식 이미지 digest `sha256:3cb4877c73b4ae5e3542c1567b6761a8913056dd429d8a18f7c40aeeb399b3b4`를 사용한다. passive BBR observer patch와 정책을 합친 전체 patch를 깨끗한 소스에 적용할 수 있게 보존한다.

각 실행은 실제 source diff·binary/library·설정·schedule·기하 CSV·제공 state·runner·실행 commit·출력 hash와 wall time을 남긴다. actual `RecvFrom` 앱 수신량을 primary goodput으로 쓰고 ACK progress와 섞지 않는다. 흐름/port·앱 누계·queue enqueue/dequeue/pending 보존을 확인한다. 큐 대기는 양방향 device 방문별 통계이며 종단간 대기와 다르다. drop layer별 hook events를 합쳐 고유 패킷 손실로 부르지 않는다. BBR 상태 표본의 loss-byte 누계 역시 고유 손실·재전송 수가 아니다.

off 실행의100Mbps 기존 측정 CSV를 이미 공유된 원본 조건의 SHA와 비교한다. 이는 동일 조건 한 건의 호환 확인이며 모든 조건 무영향의 증명은 아니다. on 실행에서는 정책이 실제 ProbeBW target을 바꿨는지 별도 state trace로 확인한다. 수신량 감소·큐 증가·손실 비용과 작은 또는 없는 효과도 그대로 남긴다. 운영자 힌트 전달과 예측 오차는 아직 구현하지 않은 배포 한계다.

**이 정책에서 처리량 개선은 확인하지 못했다.** 100Mbps의 전체 실제 수신량은 둘 다452,307,420B다. 정책은376개의 활성 기록 표본에서 목표값을 실제로 바꿨고, BBR 상태 CSV549행 중347행의 cwnd 값이 달랐다. 그러나 나머지 BBR 상태 열은 같았으며 앱 수신·RTT·ACK progress·flow summary·drop·queue/pending·coverage 등8개 측정 CSV는 바이트 단위로 같았다. 목표값을 바꿨다는 사실이 네트워크 서비스 개선을 뜻하지 않는다.

10Mbps에서도370개의 활성 표본에서 목표값이 바뀌었다. 실제 수신량은45,851,880→45,850,500B로1MSS(1,380B) 적었다. TcDrop hook events는 전체173→172, 단축 평가창1→0이었다. 10–40초 최대 served queue visit은114.647860→90.090107ms로 줄었지만 평균은 증가했다. 따라서 손실·최대 대기의 작은 감소와 평균 대기/마감 수신량 비용이 섞인 결과이며, 전반적인 지연·처리량 개선으로 요약하지 않는다. 40초 뒤의 도착/완료를 시험하지 않았으므로1MSS 차이를 영구 손실이라고도 부르지 않는다.

목표식에 기하 RTT를 넣어도 BBR의 **측정 RTprop를 덮어쓰거나 큐를 기준값에 숨기지는 않는다**. 측정 RTprop·SRTT와 실제 queue 통계는 그대로 남겼다. 반대로 다른 송신·복구 결과는 cwnd 변화의 ACK/큐 피드백으로 달라질 수 있다. 기본 복구 코드와 우선 처리 분기는 유지했으며, 네트워크 반응까지 원본과 동일하다는 뜻은 아니다. 기하 표는100ms 표본 유지이고 RTT는1µs 단위로 반올림된 양방향 전파 값이다. 연속 시각의 실제 패킷 지연을 정확히 예언하는 입력이 아니다.

- [각 실행 manifest·state trace](assets/20261012-orbit-bdp/evidence/)에 실제 실행 당시 commit·runner/정책 파일 hash·source diff·binary/library·입력·명령·원본 출력 hash를 보존했다. `repo_dirty=true`를 숨기지 않는다. 실행 중 정책 소스·runner·geometry·binary는 바꾸지 않았다. 후처리 도구 hash는 별도로 기록한다.
- 100Mbps off 실행의 cwnd/RTT/progress/flow4개 CSV가 이전 원본 조건과 byte-identical이다. 이것은 새 실제 실행의 호환 확인이고, 이전 결과를 새 on 실행으로 대체한 것이 아니다. on의 내부 cwnd 차이와 두 속도의 비용은 새 실행에서 측정했다.
- 실제 simulation wall time은 baseline100 79.1572초, policy100 65.4186초, baseline10 6.7946초, policy10 6.2446초로 합계157.6150초다. 기하 재생성·빌드·분석·압축 비용은 별도다. 최초 build는 namespace 배치 오류로 실패했고 simulation 전에 수정해 재빌드를 통과했다. 실패 patch를 별도로 보존했다.
- [원본 inventory](assets/20261012-orbit-bdp/evidence/raw-inventory.json)는76개 member, 미압축29,386,306B를 실제 압축 안에서 모두 size/SHA 검증했다. 원본은 전용 컨테이너의 `/tmp/orbit-bdp-20261012.tar.gz`, 7,743,962B, SHA `7e284e9331b17a84c9df5d6206ba467626c7ac6778aebb45353bcbefb30b02db`다. build와 constellation state는 포함하지 않으며 아직 이 track에서 외부 업로드하지 않았다.

[재현 README](../../code/orbit-bdp/README.md)의 한 complete patch와 네 실행·분석 명령을 따른다. 이번 실험은 새 공식 volume에서 수행했지만, 결과를 독립적인 두 번째 volume에서 다시 재생한 것은 아니다. 같은 deterministic 조건의 네 실행이며 seed 반복·통계적 유의성·다른 경로·예측 오차·혼합 경쟁 검증은 없다.

이 후보의 작은 실제 구현·대조는 완료했다. 현재 조건에서 더 큰 효과가 나올 때까지 gain·queue·힌트 시점을 바꾸는 sweep은 하지 않는다. **이 특정 ProbeBW BDP 목표 교체에서 이득이 없거나 혼합 비용이 있었으며, 궤도 정보로 전파/큐 성분을 구분하거나 측정 시점을 조절하는 모든 다른 정책을 반증한 것은 아니다.** 다른 track과 팀 주제·제출 범위의 선택은 별도 검토 사항이다.
