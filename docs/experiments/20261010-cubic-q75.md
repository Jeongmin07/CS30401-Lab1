# CUBIC queue-size check: 75-packet buffer

**Status:** completed exploratory experiment on 2026-10-10. This extends, but does not replace, [Seongchan's independent study](../../code/kim-study/README.md). It is not an agreed team result or a statistical generalization.

## Question and setup

The recorded 10-Mbit/s Seoul–London CUBIC study found a small whole-run gain with a 100-packet queue and a loss with a 50-packet queue when it temporarily raised the SACK/duplicate-ACK loss threshold from 3 to 20 near two route changes. Does the same intervention help at an intermediate **75-packet queue**? If not, which scheduled window changes the outcome?

All six runs used the official 200-second Seoul–London state, nodes 1584→1585, one 100-GB bulk flow, `TcpCubic` with the course SACK/PRR implementation, a 10-Mbit/s link, the same 0.1-second routing updates, and canonical version-6 `ns3.patch`. The baseline has no study parameters. The guarded run requests threshold 20 at 26.1–26.5 s and 74.9–75.3 s; the two extra 75-packet controls request only the first or second interval. The protection may restore later than the requested end. The queue is the only network parameter changed from the recorded 100-packet pair.

## Measured results

Goodput is unique bytes delivered to the receiver application, divided by 200 s or by the fixed 2.5-second event window. `Retx` and `recovery` are trace counts, not the number of independent loss episodes. The 100-packet pair is a **fresh local replay** of recorded cases. All values below came from successful ns-3 runs and [`results.csv`](assets/cubic-q75-20261010/results.csv).

| Queue | Requested protection | 200-s goodput, Mbit/s | Change from same-queue baseline | 25.7–28.2 s goodput, Mbit/s | Retx / recovery in first window | Whole-run retx / recovery | Drop trace rows |
| ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | none | 9.5443560 | — | 9.485568 | 3 / 1 | 523 / 41 | 499 |
| 100 | both | 9.5465088 | +0.0226% | 9.622464 | 0 / 0 | 507 / 40 | 486 |
| 75 | none | 9.5105184 | — | 9.335424 | 2 / 1 | 464 / 43 | 440 |
| 75 | both | 9.4915296 | **−0.1997%** | 9.622464 | 0 / 0 | 477 / 44 | 454 |
| 75 | first only | 9.4915296 | **−0.1997%** | 9.622464 | 0 / 0 | 477 / 44 | 454 |
| 75 | second only | 9.5104080 | −0.0012% | 9.335424 | 2 / 1 | 464 / 43 | 440 |

**Observation:** At 75 packets, guarding the first window removes the two local retransmissions and one recovery entry and raises delivery in that window by 3.0747%. Yet full-run delivery is 474,720 bytes lower than baseline (−0.1997%), with 13 more retransmission rows, one more recovery entry, and 14 more drop rows. First-only and both-window runs have the same displayed delivery and count metrics; second-only is nearly identical to baseline over the full run. This isolates the first requested intervention as the source of the persistent difference **in this deterministic configuration**. It does not establish which later packets or queues cause the 200-second penalty; that needs a time-series and packet-level audit.

**Interpretation limit:** This adds one intermediate queue value, not a monotonic queue threshold or confidence interval. The published 50-packet pair (9.1782696→9.144708 Mbit/s) was **not** rerun here. A positive local event result does not imply a positive whole-run result. The queue drops are observed trace rows; their mechanism and uniqueness need the same care described in the original study. We did not test random seeds, other paths, traffic mixes, TCP stacks, or imperfect route notifications.

## Reproduce and inspect

Run from the repository root in PowerShell. Use a fresh Docker volume, or new case names in an already patched study container. The course image digest is `sha256:3cb4877c73b4ae5e3542c1567b6761a8913056dd429d8a18f7c40aeeb399b3b4`; the patch SHA-256 is `473dd0e23447a58bd7ce644507cf4aa24b612020ff1e6029f5bfdb22e2cd4245`. These experiments used code from `main` commit `14a7753` before this experiment branch was made. The installed binary hash is recorded in `results.csv`.

```powershell
$studyRoot = (Resolve-Path .\code\kim-study).Path
$image = 'ghcr.io/yeonjong21/cs30401-lab1@sha256:3cb4877c73b4ae5e3542c1567b6761a8913056dd429d8a18f7c40aeeb399b3b4'
docker run -d --name cubic-q75-replay --mount "type=bind,source=$studyRoot,target=/work" --mount 'type=volume,source=cubic-q75-replay-ns3,target=/home/ubuntu/ns-3.48' $image sleep infinity
docker exec -w /home/ubuntu/ns-3.48 cubic-q75-replay bash -lc 'git apply --check /work/ns3.patch && git apply /work/ns3.patch && ./ns3 build'
docker exec cubic-q75-replay python3 /home/ubuntu/lab/scripts/path_truth.py /home/ubuntu/lab/data/seoul_london/state dynamic_state_100ms_for_200s 1584 1585 /work/path_truth_200s.csv

# Published 100-packet controls (the complete recorded settings come from their manifests):
docker exec cubic-q75-replay python3 /work/replay_cases.py leo10-base leo10-guard20 --workers 2
docker exec cubic-q75-replay python3 /work/analyze_replay.py

# Four new 75-packet conditions:
docker exec cubic-q75-replay python3 /work/run_study.py q75-base --kind leo --cc TcpCubic --rate 10 --queue 75 --duration 200 --trace 1
docker exec cubic-q75-replay python3 /work/run_study.py q75-guard20 --kind leo --cc TcpCubic --rate 10 --queue 75 --duration 200 --trace 1 --parameters 'study_threshold=20;study_windows=26100000000:26500000000|74900000000:75300000000'
```

The output CSV and raw-input hashes correspond to [`assets/cubic-q75-20261010/`](assets/cubic-q75-20261010/). The four new full-analysis and raw-input hashes are in the CSV/JSON so a teammate can compare a rerun.

On another laptop, the Docker commands above regenerate them. The local container and ns-3 volume are retained for further inspection. No change was made to Seongchan's patch or published 75-case evidence.
