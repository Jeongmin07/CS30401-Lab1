# 예측 가능한 LEO 정보를 이용한 선제적 TCP 송신 조절

작성: kim-seongchan, 2026-10-12. `research/bbr-route-transition`에서 [PR16](https://github.com/Jeongmin07/CS30401-Lab1/pull/16)의 방향 검토를 보완한다. **후보와 검증 계획이며, 새 알고리즘 구현·성능 개선·최종 팀 주제 확정을 뜻하지 않는다.**

## 과제는 미래 경로 정보를 쓰는 접근을 허용한다

[Handout 4쪽 STEP 2](../CS30401_26F_Lab1_Handout.pdf)는 위성 위치와 경로가 바뀔 시각처럼 TCP가 보통 모르는 정보를 사용할 수 있다고 명시한다. 공개 궤도로 계산하거나 운영자가 알려 주는 방법을 예로 들며, 누가 정보를 필요로 하는지, 현실적인 획득 방법, 필요한 정확도와 배포 비용을 설명하도록 요구한다.

[Environment Guide 14쪽 §5](../CS30401_26F_Lab1_Environment_Guide.pdf)에도 미래 경로 변화를 미리 아는 접근과 운영자의 forwarding 변경이 있다. 앞선 검토에서 이 허용 범위를 충분히 반영하지 못했다. 13쪽 표는 수정 위치 안내이지, 정해진 해법 목록이나 효과 보증이 아니다.

따라서 정보 획득 가정을 명시한 궤도 기반 정책은 과제 범위에 맞는다. 다만 **위치 예측 가능성, 실제 경로 예측 가능성, 패킷의 실제 도착 시각 예측 가능성은 서로 다르다.** 궤도만 알아도 운영자의 경로 선택·갱신 정책이나 현재 큐를 자동으로 알게 되는 것은 아니다. 시뮬레이터의 정확한 미래 상태를 준 경우는 이상적인 힌트를 받은 조건으로 표시하고, 곧바로 현실의 TCP 송신자가 그 정보를 갖는다고 주장하지 않는다.

## 기존 방향에서 바꿀 부분

단순히 경쟁 흐름이 늘었을 때 BBR의 이전 최대 대역폭 추정이 늦게 적응한다는 가설은 단독 주방향에서 중단한다. 같은 입력 변화는 지상 고정 병목에서도 생긴다. 경로 합류를 연구할 수는 있지만, 위성 기하의 예측 정보가 어떤 추가 이점을 주는지가 필요하다. 기존 BBR 계측·대조 기록은 보존하며 실패한 가설을 개선 성과로 바꾸어 쓰지 않는다.

새 우선 질문은 **예측된 경로 변화 직전에 TCP의 실제 송신을 조금 조절하면, 변화 후 발생할 수 있는 패킷 추월과 불필요한 손실 반응을 줄일 수 있는가**이다. 기본 모델은 100ms마다 경로를 갱신하고 전환이 순간적이며, handover 단절·무작위 무선 오류·링크 용량 변동을 포함하지 않는다. 이 모델에서 생기는 문제를 먼저 확인한다.

이전 Vegas의 RTT 기준 갱신 결과와 CUBIC 복구 실험은 원본과 함께 남긴다. 이번 후보의 효과를 뜻하지 않으며, 다른 조원의 연구·PR을 취소하거나 팀의 역할을 새로 배정하는 문서도 아니다.

## 후보 1: 경로 단축 직전 새 데이터 송신을 조절한다

먼저 보낸 패킷이 긴 경로를 지나고, 나중 패킷이 짧은 경로를 지나면 나중 패킷이 먼저 도착할 수 있다. 수신자가 보내는 ACK/SACK를 송신자가 손실로 해석하면 필요 없는 재전송·복구가 발생할 수 있다. 이 후보는 경로 단축 전에 새 데이터의 pacing 간격을 늘리거나 짧게 쉬어 **재정렬의 발생 자체를 줄이는 방법**이다. 기존 K8/K20처럼 손실 판정 문턱을 높여 재정렬을 더 오래 기다리는 방법과 다르다.

관련 현상은 기존 단일 흐름 기록에 있다. [26.2초 증거 CSV](../../code/kim-study/evidence/event26_evidence.csv)의 `leo10-base`는 10Mbps·q100·200초 서울–런던, CUBIC/SACK/PRR·기본 K3 조건이다. 원본 전송 `tx_id=21859`의 TX/RX는 26.195610854/26.283909347초, `21862`는 26.200199611/26.278173331초다. 각각의 실제 지연은 88.298493/77.973720ms다. 나중 패킷이 4.588757ms 뒤에 송신됐지만 **5.736016ms 먼저 도착했다.** 원자료 행은 송신 33817/33822, 수신 21552/21547로 명시되어 있다.

같은 [기하 경로 기록](../../code/kim-study/path_truth_200s.csv)의 전파 RTT는 26.1→26.2초에 97.698→91.064ms로 줄었다. 양방향 합의 절반으로 계산한 편도 근사 단축은 3.317ms다. 이를 실제 패킷 지연 차이 10.324773ms와 같다고 둘 수 없다. 실제 지연에는 직렬화·대기와 전송 중 경로 갱신의 영향도 들어가며, 이미 네트워크에 있는 패킷의 남은 경로와 큐를 기하 기록만으로 알 수 없다.

두 패킷의 도착 시각을 `a=t_tx+d`로 쓰면 순서를 유지하려는 송신 간격은 실제 `d_old-d_new` 이상이어야 한다. 이것은 관계식이지 실행 가능한 보장식이 아니다. 기하 예측값으로 대체한 간격은 **시험할 후보 값**이며, 이 패킷 쌍의 지연이나 5.736ms를 모든 전환의 안전한 pause 길이로 사용하지 않는다.

정책이 조절할 곳은 TCP가 새 데이터를 실제로 내보내는 지점이다. 애플리케이션의 쓰기만 잠깐 멈추면 소켓 버퍼에 있는 데이터가 계속 나갈 수 있다. 이미 전송한 패킷·네트워크 큐에는 소급 적용되지 않는다. 실제 손실을 복구하는 재전송과 타이머를 무조건 정지시키지 않으며, 정책의 최대 지속 시간과 원래 송신으로 복귀하는 조건을 구현 전에 정한다. **현재 이 정책은 구현하지 않았다.**

기존 문턱 변경의 성과는 작은 편이었다. [q100 기록](../../code/kim-study/PHASE2_NOTE.md)은 같은 10Mbps·단일 흐름에서 K20과 크기 예외 정책의 첫 평가창 `[25.7,28.2)` 앱 goodput이 약 1.44% 늘었지만, 200초 전체는 약 0.023% 증가했다. [q75 기록](../experiments/20261010-cubic-q75.md)은 첫 평가창 약 3.07% 증가에 비해 전체 약 0.20% 감소였다. 이 숫자는 새 송신 조절의 예상 효과가 아니다. 국소적인 불필요한 재전송 감소만으로 전체 성능 개선을 주장할 수 없다는 배경이다.

이 후보를 1순위로 두는 이유는 제공 모델 안의 확인된 현상과 궤도 예측 정보를 직접 연결하기 때문이다. 의미 있는 이득이 나온다는 보장은 없다. CUBIC 기록은 출발 증거이며 BBR에서도 같은 비용이 발생한다고 가정하지 않는다. 선택한 TCP 구현의 관련성·시의성은 별도로 설명하고, 과제 복구 스택의 결론을 현대 Linux 전체에 일반화하지 않는다.

## 후보 2: 예측 전파 지연을 BDP·측정 시점에 활용한다

BDP는 대역폭과 RTT의 곱으로, 전송 중에 있어야 링크를 채울 수 있는 데이터량의 기준이다. 경로가 길어질 때 옛 최소 RTT 때문에 BBR의 in-flight 한도가 부족해진다는 직관은 확인할 가치가 있지만, 과제 `TcpBbr`의 ProbeBW cwnd gain은 2다. 한도를 단순히 `대역폭×옛 최소 RTT`라고 놓으면 틀린다.

[제공 기하의 소스 점검](../experiments/assets/20261012-bbr-route/alternative-source-screen.json)에서 전파 RTT 범위는 87.454–98.535ms이며 비는 약 1.1267로 2보다 작다. 대역폭 추정이 정확하고 다른 제한이 없다는 조건에서는 이 변화만으로 옛 2BDP 한도가 부족해졌다고 할 근거가 약하다. 실제 cwnd 제한·복구·수신 창·큐를 확인해야 하며, 이 계산 자체는 새 TCP 실험 결과가 아니다.

이 선별은 궤도 기반 제어 전체를 부정하지 않는다. 경로가 그대로여도 위성이 움직여 전파 지연이 연속적으로 바뀐다. 예측 전파 지연으로 관측 RTT의 기하 성분과 큐 성분을 구별하거나, 경로가 짧아지기 전에 전송 중 데이터량을 줄여 과도한 큐를 예방하거나, 최소 RTT 재측정 시점을 고르는 질문은 별도로 남는다. 대역폭은 궤도만으로 알 수 없으므로 기존 추정값을 사용할지 운영자 용량 힌트를 받을지 명시해야 한다. 높은 관측 RTT를 곧바로 새 전파 기준으로 채택하면 혼잡 큐를 흡수할 수 있다. 경로 힌트가 혼잡 부재의 증거는 아니며, ProbeRTT의 송신 감소 비용과 잘못된 힌트의 비용도 남는다. **추가 측정 근거가 없는 현재는 2순위 가설로 둔다.**

## 후보 3: 앙각으로 cwnd 상한을 정한다

앙각은 지상국에서 본 위성의 지평선 기준 각도다. 낮은 앙각이 현실의 무선 품질과 관련될 수 있어도, 기본 모델은 링크 용량이 일정하고 SNR·MCS에서 용량을 계산하지 않는다. 따라서 앙각에 비례한 cwnd 제한을 넣으면 검증된 링크 품질 적응보다 임의의 전송 제한이 될 수 있다. 각도→용량 관계를 외부 근거와 함께 새로 모델링해야 하므로 현재 우선 후보에서 제외한다.

기본 모델에서 앙각은 가시성·접속 가능한 위성과 관련되므로, **다가올 접속 위성 변화나 경로 변경의 힌트**로 쓰는 편이 더 직접적이다. 그래도 실제 경로 갱신 정책이 필요하며, 낮은 각도만으로 손실·단절을 가정하지 않는다.

가능한 기여는 예측성 자체의 발명보다 **과제의 특정 경로 전환에서 작은 송신 정책이 줄인 비용과 새로 만든 비용을, 필요한 정보의 한계까지 포함해 검증한 것**이다. 문제가 작거나 순서를 바꾸는 비용이 더 크면 그 결과로 후보를 중단한다.

## 다음 검증은 작게, 원인부터 한다

1. **기본 동작:** 선택한 한 경로 전환에서 원본 송신·수신 순서, 실제 drop, ACK/SACK와 복구를 연결한다. 경로 단축만 있고 불필요한 반응·서비스 비용이 없으면 이 후보의 구현으로 넘어가지 않는다. 기존 26.2초 원본 도착 증거를 재사용할 수 있지만 다른 TCP의 문제를 대신 입증하지는 않는다.
2. **작은 정책:** 이상적으로 알려 준 전환 시각·기하 지연만 입력으로 받아 새 데이터 송신 한 곳을 바꾼다. 큐 정답·미래 실제 도착 시각을 몰래 입력하지 않는다. 기본 off, 적용 범위, 복귀 조건과 정확한 실행 소스를 기록한다.
3. **맞춘 대조:** 동일한 routing·트래픽·링크·시드에서 off/on을 비교한다. 변화가 없는 때의 힌트와 잘못된 시각의 힌트도 대조한다. 다른 경로로 우회시켜 얻은 효과를 송신 정책의 효과로 섞지 않는다.
4. **효과와 비용:** 미리 정한 전환 평가창과 전체 앱 수신 goodput, 불필요한 재전송·복구, 큐·지연을 함께 본다. 유한 크기 흐름의 완료 시간(FCT), 실제 손실의 복구 지연, 경쟁자가 받는 서비스도 확인한다. pause가 만든 전달 지연을 평가창 밖으로 숨기지 않는다.
5. **정보 오차:** 경로 갱신의 100ms 간격과 전파 단축 규모를 근거로 시각·지연 예측 오차 범위를 미리 정해 평가한다. 운영자 정보 전달 지연·누락·오탐, 공개 궤도와 실제 routing의 차이를 설명한다. 하나의 정확한 힌트에서만 효과가 나면 이상적 조건의 결과로 제한한다.

확인되지 않은 문제를 만들기 위해 도시·시간·큐·정책 값을 대규모로 탐색하거나 무선 모델까지 한꺼번에 늘리지 않는다. 한 전환에서 원인과 작은 효과를 확인한 뒤 제한적인 추가 조건으로 검증하고, 전체 이득이 작거나 비용이 크면 정직하게 중단한다. PR 검토와 다른 조원의 동의, 최종 보고서·제출 ZIP 준비는 이 후보 검토와 별개로 남아 있다.
