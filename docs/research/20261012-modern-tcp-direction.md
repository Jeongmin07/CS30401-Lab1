# 현대 TCP와 위성 경로 합류를 중심으로 한 방향 재평가

**최신 상태:** 이 문서는 초기 BBR 합류 가설의 근거와 검증 계획을 보존한다. 사용자의 후속 인과관계 검토를 반영해 대역폭 감소만을 근거로 한 주가설은 중단했다. 현재 판단은 [예측 정보를 활용하는 방향](20261012-predictable-leo-tcp.md)과 [PLAN](../PLAN.md)을 먼저 읽는다. 아래의 후보·관측 전 문구를 현재 실행 명령이나 승인된 개선으로 해석하지 않는다.

작성: kim-seongchan, 2026-10-12. 기준은 `main`의 `b60e8e019053c7d33b853510ec06c3d94ee78faf`이며, 작업 브랜치는 `research/bbr-route-transition`이다.

사용자는 과제 원문과 최신 연구를 다시 확인한 뒤 현대 TCP의 실제 LEO 문제를 중심으로 방향을 수정하고, 이 판단과 조기에 중단할 대안까지 PR로 공유하도록 요청했다. 이 문서는 **연구 방향과 검증 순서**를 기록한다. 새 BBR 실험의 성능 결과, 개선 구현 완료, 다른 조원의 동의나 최종 팀 주제 확정을 뜻하지 않는다.

## 왜 방향을 바꾸는가

[과제 원문](../CS30401_26F_Lab1_Handout.pdf)의 4쪽은 기존 최신 TCP 구현을 고려하고 선택의 관련성과 시의성을 정당화하도록 요구한다. STEP 3의 비교 기준은 같은 시나리오에서 아이디어를 적용하지 않은 구현이다. 따라서 모든 최신 TCP를 이기는 처리량이 필수 조건은 아니지만, 오래된 구현의 약점을 고쳤다는 사실만으로 그 구현을 선택한 이유가 충족되는 것도 아니다.

기존 Vegas 연구는 오래된 RTT 기준의 문제와 기준 갱신의 이득·혼잡 오인 비용을 재현했다. 그러나 갱신 원리는 선행연구에 있고, 현재 위성망에서 Vegas를 선택할 실용적 이유나 현대 TCP보다 나은 목표를 충분히 검증하지 못했다. **이번 사용자의 핵심 연구 후보에서는 Vegas 개선을 제외한다.** 코드, 실험, 원본, 재현 기록은 보존하며 후속 연구의 대조·한계 자료로 사용할 수 있다. 이 판단은 기존 결과가 틀렸다는 뜻이 아니고 다른 조원의 연구 범위를 취소하는 지시도 아니다.

과거 `shared-results/`의 BBR 약 93Mbps는 탐색 실행의 요약이다. pacing은 켜져 있지만 상세 이벤트 로그와 실행 소스·patch 정보가 충분하지 않아, 새 실험의 원인 분석이나 완전히 맞춘 비교군으로 사용할 수 없다. 평균이 높은 BBR에도 짧은 구간의 서비스 손실, 큐 지연, 경쟁자 피해가 있을 수 있다. 반대로 그런 문제가 실제로 없을 수도 있다. 어느 쪽도 현재 요약만으로 확정하지 않는다.

## 먼저 고정할 환경과 구현 범위

- 공식 환경은 `ghcr.io/yeonjong21/cs30401-lab1:2026f-v1`, ns-3.48과 제공 Hypatia 모듈이다. 자세한 모델·제출 조건은 [과제 참고 문서](../LAB_REFERENCE.md)를 따른다.
- 기본 경로는 지상국–위성–ISL–위성–지상국이며, 지상 인터넷 구간과 PoP는 없다. 제공 상태는 200초이고 경로는 100ms마다 갱신된다.
- 경로 전환은 순간적으로 일어난다. 기본 handover 단절, 무작위 무선 오류, 시간에 따른 링크 용량 변화는 없다. 순간 전환에서도 패킷 순서·전파 지연·어떤 흐름이 같은 링크를 쓰는지는 바뀔 수 있다.
- 이번 BBR 대상은 과제의 `TcpBbr`, 즉 **BBRv1 계열 구현**이다. 선택 이유는 제공 환경에서 최대 대역폭 추정과 주기적 탐색을 직접 추적·대조할 수 있고 최근 위성 실측에서도 비교 대상으로 다뤄지기 때문이다. 이것이 BBRv3를 대신하는 최신 구현이라는 뜻은 아니다. BBRv3의 손실 반응이나 Linux 전체 스택을 실험했다고 쓰지 않으며, 과제 버전에서 얻은 결론의 범위를 밝힌다. 소스·설정·실행 파일의 실제 식별 정보를 실험 기록에 남긴다.
- 컨트롤러 입력과 분석용 정답을 구분한다. 시뮬레이터의 경로·큐 기록은 원인 검증에 사용할 수 있지만, endpoint 알고리즘이 그 정보를 이미 알고 있다고 가정하지 않는다.

## 주방향: 자연스러운 경로 합류 뒤 BBR의 추정과 탐색

**질문:** 위성 이동으로 별개 경로의 흐름들이 새로운 공유 병목으로 합류할 때, 기존 BBR의 최대 대역폭 추정과 증가 탐색이 늦게 적응하여 큐·손실·분배 비용을 만드는가? endpoint에서 얻을 수 있는 정보만으로 그 비용을 줄일 수 있는가?

이것은 아직 관측 전 가설이다. 물리 링크 속도가 같아도 공유 흐름이 바뀌면 각 흐름이 받는 서비스는 바뀔 수 있다. 다만 각 흐름의 몫을 곧바로 `링크 속도/흐름 수`라고 단정하지 않는다. RTT, 탐색 단계, ACK, 큐와 경쟁자의 동작이 실제 분배를 결정한다.

가설의 연결은 다음과 같다.

1. 두 흐름이 이미 전송 중이며, 이전에는 서로 다른 병목을 사용한다.
2. 정상적인 경로 갱신으로 같은 **방향의 실제 송신 장치/큐**를 공유하게 된다.
3. BBR이 이전에 관측한 최대 전달률을 유지하거나 증가 탐색을 계속한다.
4. 그 상태가 실제 병목의 과도한 유입, 큐 대기·drop, 상대 흐름의 서비스 저하로 이어진다.

위 네 단계는 각각 확인해야 한다. 같은 위성 노드를 지나거나 반대 방향 링크를 쓰는 것은 같은 큐 공유의 증거가 아니다. 후속 흐름을 80초에 시작하는 기존 고정 병목 실험은 유용한 경쟁 대조이지만, 위성 이동 때문에 경로가 합류한 실험은 아니다. 경로 후보에 필요한 지상국이 제공 상태에 없다면 상태 생성 조건과 명령을 따로 정당화한다.

BBR의 오래된 추정이 남아 있다는 사실만으로 버그나 성능 문제가 증명되지는 않는다. ACK 압축, 재정렬에 따른 복구, 수신 창 제한, 송신 애플리케이션의 제한, 초기 기동이 원인일 수도 있다. 탐색 gain이 1보다 큰 것도 원래 설계의 일부다. **그 설계가 이 경로 변화에서 만드는 실제 비용과 회복 지연**이 연구 대상이다.

## 관측에서 개선까지 넘어가는 기준

| 단계 | 할 일과 필요한 증거 | 넘어가지 않을 조건 |
|---|---|---|
| 경로 확인 | 기존 경로 상태에서 두 흐름의 전환 전후 경로와 공유 송신 장치·방향·기간을 찾는다. 두 흐름은 합류 전에 이미 활성이다. | 실제 공유 병목이 없거나 공유가 너무 짧아 전달·큐 반응을 분리할 수 없으면 이 후보를 중단한다. 결과가 나올 때까지 도시·시작 시각을 계속 바꾸지 않는다. |
| 기본 동작 관측 | 원래 BBR을 사용해 모드, 대역폭 표본과 최대 추정, 탐색 단계/gain, pacing, in-flight, cwnd, 실제 RTT와 평활화 RTT, 앱 수신량, 큐·drop·재전송을 같은 시간축으로 확인한다. | 평균 처리량 차이만 있고 경로 합류·추정·유입·비용의 연결이 없으면 개선 구현으로 넘어가지 않는다. |
| 원인 대조 | 같은 병목을 처음부터 공유하는 경우, 경쟁이 없는 경우, 가능하면 합류하지 않는 경로를 비교한다. 기동·정상 경쟁·경로 합류를 구분하고 실제 손실과 재정렬도 확인한다. | 잘못된 경로/trace 연결, 회복·pacing 구현 차이 또는 단순히 흐름이 늘어난 정상 분배만으로 설명되면 가설을 수정하거나 중단한다. |
| 작은 개선 | 확인된 원인 한 곳만 바꾼다. 후보는 오래된 최대 추정의 유지 또는 증가 탐색의 과도한 지속 중 실제로 비용을 만든 부분이다. 필요한 endpoint 정보, 판단 오차, 기본 off 동작을 먼저 선언한다. | 현재 구현에 없는 네트워크 정답·미래 경로·flow 수를 몰래 입력해야 효과가 나면 실용적 개선으로 채택하지 않는다. |
| 효과와 비용 평가 | 같은 경로·트래픽·환경에서 아이디어를 끈 baseline과 비교한다. 합류 구간과 전체 수신량, 양쪽 흐름의 서비스, 합계, 큐, drop, 재전송과 회복 시간을 함께 본다. | 자신의 몫만 늘고 합계·지연·상대 흐름에 설명되지 않는 비용이 생기면 성공으로 요약하지 않는다. 불리한 조건도 남긴다. |
| 종료와 재현 | 선택한 결과를 새 공식 환경에서 재현하고 실제 실행 코드·patch·설정·원본 식별 정보를 보존한다. 주가설이 실패하면 짧게 실패 이유를 기록하고 아래 대안 하나만 점검한다. | 새 문제가 보일 때마다 전체 알고리즘/파라미터 목록을 늘리지 않는다. 통과하지 않은 관측을 보고서의 입증된 문제로 쓰지 않는다. |

기본 구현의 상태 관측은 정책 변경과 구별하며, 계측을 켜고 끈 결과의 호환을 확인한다. 분석 시 창은 `[시작,끝)`으로 선언하고 두 흐름이 함께 활성인 구간에서 분배를 비교한다. Jain 지수는 전달률의 균등함을 보는 한 지표이며 보편적 공평성의 정의는 아니다. 앱 수신 goodput과 ACK된 바이트, wire 수신, TCP 수신 버퍼 수용을 혼용하지 않는다. RTT에서 전파 지연을 뺀 값도 직접 측정한 큐 대기와 동일하다고 가정하지 않는다.

개선 전에는 시뮬레이터가 아는 정확한 경로 시각을 이용해 원인과 가능한 효과의 상한을 살펴볼 수 있다. 그 대조는 **정답 정보를 준 진단**으로 별도 표시하며, 실제 endpoint 정책의 성과와 합치지 않는다. endpoint 탐지로 바꿀 때는 오탐·누락·지연이 만드는 비용도 평가한다.

| [2026년 경로 단계 경계 논의](https://www.ietf.org/archive/id/draft-lai-ccwg-lsncc-01.html), §3.2·4.1–4.2·5 | 경로 재구성 전후의 대역폭·RTT 극값을 섞지 않는 방향과 PoP 응답 간격 기반 힌트를 논의한다. 최신 확인 버전 01은 2026-09-01 만료된 개인 Internet-Draft다. | 신호의 모호성과 추정 신선도를 설명하는 근거다. 경계 힌트는 혼잡이 없다는 증거가 아니며 RFC나 IETF 승인 해법도 아니다. 용량 변동·무선 손실 관련 결과는 현재 기본 모델의 관측으로 바꾸어 쓰지 않는다. |
| [2026년 실제 Starlink TCP 비교](https://arxiv.org/html/2607.07133v1), §III | 2026년 4월에 9개 구현의 단독·동시 경쟁, 상·하향을 조건별 10회·300초씩 측정했다. BBRv3는 높은 처리량과 손실·지연의 균형을 보였으며 항상 최대 몫을 얻지는 않았다. | BBR가 언제나 망가진다는 전제로 시작하지 않는다. 버전·방향·경쟁·비용을 함께 평가하는 방식을 참고한다. Linux 실측을 과제 `TcpBbr` 검증으로 쓰지 않는다. |
| [2026년 소형 언어모델 기반 BBR 제어](https://arxiv.org/html/2607.07142v1), §IV-B/C | 전체 TCP를 연결해 재생하지 않고, 예측 gain에서 처리량·재전송을 계산하는 대리 평가를 사용한다. 처리량은 `Bcap × min(gain,1)`로 계산하고 재전송도 gain 의존 식으로 추정한다. | 실제 패킷·큐·ACK 피드백 안에서 개선이 확인된 근거로는 부족하다. 모델 학습이나 정책 포팅을 추가하지 않으며, 우리 결과도 대리 점수로 실제 성능을 대체하지 않는다. |

이번 기여가 생긴다면 알려진 BBR 아이디어 자체의 발명보다, **과제의 실제 경로 합류에서 특정 문제를 확인하고 작은 변경의 효과·비용·정보 한계를 검증한 것**이다. 새로운 문제나 개선 효과가 확인되지 않으면 그렇게 기록한다.

## 주가설이 실패할 때 확인할 작은 대안

아래도 입증된 문제나 승인된 최종 구현이 아니다. 주방향의 관측이 실패할 때 한 번에 하나만 확인한다. 결과가 잘 나오는 값을 찾아 계속 바꾸는 후퇴 계획으로 사용하지 않는다.

| 대안 가설 | 먼저 확인할 조건과 실패 기준 | 검증 뒤 가능한 작은 변경 |
|---|---|---|
| CUBIC의 HyStart가 기하 RTT 증가를 혼잡으로 오인해 기동을 너무 일찍 끝낸다. | 실제 slow start 중 탐지 분기와 `ssthresh=cwnd` 변화, 큐·drop·전파 지연을 연결해야 한다. 과제 소스의 `HystartDelayThresh`는 `m_delayMin` 자체를 4–1000ms로 제한하므로 일반 Linux의 minRTT/8·16ms 상한을 가정하면 안 된다. 작은 기하 상승이 delay 분기를 켠다고 단정하지 않으며 packet-train 탐지와도 구별한다. 해당 분기가 작동하지 않으면 중단한다. | 관측된 기동 판정 한 곳의 확인 절차를 바꾸고, 실제 큐 증가·손실이 있을 때 늦어진 종료가 만드는 비용을 대조한다. 무조건 HyStart를 끄는 것을 최종 개선으로 삼지 않는다. |
| BBR의 RTprop 갱신이 경로 지연 상승 뒤 늦어져 실제 전송을 제한한다. | 오래된 최소 RTT뿐 아니라 cwnd 제한과 실제 서비스 손실이 함께 있어야 한다. ProbeBW의 cwnd gain은 2이며 패킷 단위 여유도 있어 in-flight 한도를 단순 `BtlBw×minRTT`라고 쓰면 틀린다. 예를 들어 RTT 90→100ms는 옛 2BDP 한도 안에 들어갈 수 있으므로 변화만으로 제한을 입증하지 못한다. | endpoint 신호로 기존 ProbeRTT 재측정을 앞당기는 후보를 분리한다. 높은 RTT를 바로 새 기준으로 채택하지 않고, 탐지 오류·지속 경쟁 큐·probe 비용을 평가한다. |
| BBR의 ProbeRTT 자체가 짧은 서비스 손실을 만든다. | 실제 모드 진입·낮은 in-flight·수신량 감소가 이어지는지, 그리고 그 비용이 정상적인 최소 RTT 측정 비용 이상인지 확인한다. 단순히 주기적 dip이 있다는 이유만으로 결함이라고 하지 않는다. | 측정의 유효성을 유지한 채 시점이나 불필요한 중복 진입을 제한할 수 있는지 검토한다. 측정을 없애고 처리량만 높이는 변경은 RTT·큐·분배 악화를 함께 평가해야 한다. |

구현 확인의 기준은 이번 읽기에서 확인한 공식 이미지의 ns-3 HEAD `99bc6f733274475b7a6e804128651e17ee2a2536`이다. `tcp-bbr.cc`의 대역폭 창 10회, RTT 창 10초, ProbeRTT 200ms와 ProbeBW cwnd gain 2, `tcp-cubic.cc`의 위 HyStart 제한값을 확인했다. 이것은 소스 기본값 확인이며 새로운 시뮬레이션 성과가 아니다. 실제 실행에는 runner가 덮어쓴 설정과 전체 적용 patch도 별도로 기록한다.

## 기존 PR과 다른 조원의 작업을 어떻게 다루는가

- [PR10](https://github.com/Jeongmin07/CS30401-Lab1/pull/10)은 기존 CUBIC 추적·대조이고, [PR11](https://github.com/Jeongmin07/CS30401-Lab1/pull/11)은 넓은 문헌·맥락 정리다. 이미 수행한 작업을 읽고 필요한 분석 방법만 명시적으로 재사용한다.

- [PR15](https://github.com/Jeongmin07/CS30401-Lab1/pull/15)는 Jeongmin07의 Vegas-A 비교·갱신 민감도·연구 패키지 재현이다. 마지막으로 확인한 `4c3d86f`에는 r40 지연 상승 및 경쟁 시작 시각 대조가 선언됐지만 결과는 대기 상태다. 이 사용자의 방향 변경으로 다른 조원의 실행·PR·문서를 임의로 취소하거나 수정하지 않는다.
- 이번 변경은 방향과 가설을 공유한다. 기존 PR의 병합, 역할 배정, 팀 최종 주제, [공통 PLAN](../PLAN.md)의 합의 상태는 별도 판단이다. 다른 AI의 검토는 다른 조원의 실제 동의를 뜻하지 않는다. 각 노트북의 미공유 실행 상태는 추측하지 않는다.

현재 완료한 것은 과제·문헌·실제 소스의 재검토와 이 검증 계획이다. **아직 주장할 새 처리량·지연·분배 개선 수치는 없다.** 앞으로의 우선순위는 자연 합류와 기본 동작의 짧은 확인, 원인 대조, 필요한 경우에만 작은 개선이며, 실패한 가설과 중단 이유도 PR에 남긴다. 최종 영어 IEEE 보고서·팀 이름·제출 ZIP과 깨끗한 환경에서의 전체 재현은 이후 선택한 결과를 기준으로 다시 완성한다.
